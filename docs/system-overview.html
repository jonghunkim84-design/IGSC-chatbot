IGSC 인증 문의 챗봇

국제지속가능인증원(ISO/IEC 17065 인정 인증기관)의 고객 문의 응대 챗봇입니다. 고객이 인증의 가능 여부·비용·기간·절차·서류를 물으면 사람이 승인한 FAQ의 내용만 근거로 답하고, 근거가 없거나 답하면 안 되는 질문(컨설팅·불만)은 답하지 않고 담당자에게 연결합니다.

이 문서는 이 시스템을 처음 보는 개발자가 무엇을, 왜, 어떻게 만들었는지를 빠르게 파악하도록 쓴 소개 자료입니다. 구조 → 핵심 파이프라인 → 데이터·보안 → 운영·품질 순으로 읽으면 됩니다.

≈12.5k소스 코드 줄 수 (테스트 별도 ≈2.8k)
280자동 테스트 (Vitest 18개 파일)

한 문장 구조

Next.js(App Router) 한 앱이 챗봇 화면·관리자 화면·API를 모두 제공하고, Supabase(Postgres·Storage·Auth)에 데이터를 두며, Claude(Haiku 4.5 분류·선택, Sonnet 5.5 답변·초안)를 호출합니다. 호스팅은 Vercel입니다.

고객 쪽

홈페이지 위젯(Shadow DOM + iframe), 채널 링크(블로그·링크드인·인스타그램·이메일 서명)로 열리는 /chat. SSE 스트리밍 답변.

운영자 쪽

FAQ 등록·승인, 미답변 처리, 문서 업로드 → FAQ 초안 자동 생성·검수, 대화 로그, 유입 채널 통계, 운영 상태.

운영 보호

요청 제한, 보안 헤더, DB·AI 상태 점검과 알림 메일, 전체 백업 스크립트, 대표 질문 회귀 테스트.

2설계 원칙과 구현 방법

인증기관의 답변은 틀리면 안 되고, 공평성(ISO 17065)을 해치면 안 됩니다. 그래서 "모델을 믿는" 대신 구조로 강제했습니다.

원칙왜구현
승인된 FAQ로만 답한다환각 방지, 사람이 책임지는 내용만 노출검색 대상은 status='approved' FAQ만. 답변 프롬프트는 <faq> 안의 내용만 쓰도록 제한하고 근거가 없으면 [[NO_ANSWER]] 센티널을 출력 → 시스템이 담당자 이관 처리. 일부만 답할 수 있으면 [[PARTIAL]] 센티널 → 고정 연결 문구 부착
컨설팅은 거절한다인증기관은 심사 대상에게 컨설팅을 줄 수 없음(공평성)분류 단계에서 consulting이면 그 자리에서 고정 문구만 반환(모델이 답을 쓰지 않음). 복합 질문은 complaint > consulting > allowed 우선순위
비용·기간은 확정값만추정 금지값이 없는 FAQ는 needs_input(답변 비어 있음)으로 두고 승인 불가·답변 미사용. 비용·기간 FAQ에는 면책 문구 자동 첨부. 회귀 테스트가 "답변의 숫자는 근거 FAQ에 있는 값만" 기계 검사
승인은 사람만자동 생성 초안이 곧바로 고객에게 나가면 안 됨문서에서 만든 초안은 항상 draft. 승인 시 approved_by/approved_at 기록. 일괄 승인도 건별 기록
제품 인증 가능 여부는 확답하지 않는다심사 전 판단 불가가능 여부 질문(eligibility)이면 유사 인증 이력(공개 동의분)만 참고로 안내 + "담당자 검토 후 확정" 문구
모든 대화를 기록한다FAQ 개선 순환, 감사chat_log 전 건 기록. 답하지 못한 질문은 unanswered → 관리자가 FAQ로 승격하는 "선순환"
오류는 삼키지 않는다조용한 실패 방지예외는 로깅 후 고객에게는 담당자 연결 안내. 운영 상태 점검이 AI 장애(크레딧 소진 등)를 별도로 감지
핵심 아이디어 처리 순서(분류 → 분기 → 선택 → 답변 → 기록)를 단계 건너뛰기 없이 항상 거치고, 모델이 문장을 만드는 경로는 "allowed + 승인 FAQ 근거 있음" 단 하나입니다. 나머지는 전부 고정 문구입니다.

4아키텍처

요청 경로 두 가지

고객 대화

widget.js / 채널 링크 → /chat(React) → POST /api/chat → 요청 제한 확인 → runChat() → SSE(meta → delta* → done) 스트리밍. 세션은 브라우저 탭 단위 UUID, 채널은 ?src= 또는 Referer로 판정.

관리자 작업

매직링크 로그인 → middleware가 세션·허용 이메일 확인 → 서버 컴포넌트가 lib/db로 직접 조회, 변경은 서버 액션(requireAdmin() 재검증). 긴 작업(문서 초안 생성)은 클라이언트가 /api/admin/documents/[id]/generate-faq를 조각 단위로 반복 호출.

5채팅 파이프라인 (lib/chat/run-chat.ts)

한 질문이 처리되는 전체 순서입니다. runChat()은 AsyncGenerator로 이벤트(meta/delta/done)를 내보내고, 모든 외부 의존성은 ChatDeps로 주입됩니다.

1
요청 검증 · 요청 제한 app/api/chat/route.ts

JSON 파싱, 메시지 500자 제한, 세션·인증 종류·되묻기 이전 질문·채널(source) 정리. IP 해시 기준 분당 15 / 시간당 120 / 전체 일 3,000건 (초과 시 HTTP 429 + 안내). 인증 종류 이름표는 10분 캐시.

2
분류 ∥ FAQ 검색 병렬 Haiku 4.5

질문을 allowed / consulting / complaint / out_of_scope 로 분류하고 eligibility(가능 여부 질문?)·cert_specified(인증 이름 언급?)를 함께 뽑습니다. 분류가 끝나기 전에 FAQ 검색을 먼저 시작해 대기 시간을 줄이고(약 0.7s ∥ 1.7s), 분류 결과가 거절·이관이면 검색 결과는 버립니다(한국어가 아니면 검색 자체를 시작하지 않음).

3
분기 — 고정 문구 경로
consulting공평성 안내 + 외부 컨설팅 안내 (모델 미사용)
complaint접수 방법 + 연락처 (담당자 직접 대응)
out_of_scope"인증 문의 전용" 안내
한국어 아님담당자 연결 + 영문 안내
4
승인 FAQ 0건 확인

hasApprovedFaq()가 false면 검색·답변 없이 "AI 답변 준비 중입니다."(기록 안내·연락처 포함)로 종료하고 질문은 미답변 목록에 남깁니다. 확인 실패 시에는 평소대로 진행(장애 때문에 응대가 막히지 않게).

5
FAQ 선택 (+ 가능 여부면 인증 이력) Haiku 4.5 · lib/search

승인 FAQ 질문 목록 전체를 프롬프트에 넣고 관련 번호를 고릅니다(최대 5개, 6장). 인증 종류 되묻기 후속이면 이전 질문과 합쳐 처리. 가능 여부 질문이면 같은 인증의 공개 동의된 이력에서 유사 제품군을 별도로 선택.

6
답변 생성 (스트리밍) Sonnet 5.5 · max_tokens 1500

선택된 FAQ(질문·답변)만 컨텍스트로 전달. 앞부분을 버퍼링해 센티널을 판정한 뒤 고객에게는 제거해서 내보냅니다. 출처 링크·면책 문구·이력 블록은 시스템이 조립해 붙이므로 모델이 쓰지 않습니다.

answeredFAQ 근거 답변 + 출처 + 필요 시 면책
answered (partial)[[PARTIAL]] → 가능한 범위까지 + 고정 연결 문장 + 미답변 기록
handoff[[NO_ANSWER]]/근거 없음/needs_input 항목/오류
clarify인증 종류 모를 때 되묻기 + 선택 버튼
7
기록 chat_log · unanswered

질문·답변·근거 FAQ id·처리 결과(route)·유입 채널(source)을 chat_log에, 답하지 못한 질문은 unanswered에 남깁니다. 기록 실패도 삼키지 않고 로깅하며, 실패해도 고객 응답은 이미 전달된 상태입니다.

6FAQ 검색 방식 — 임베딩 없는 "프롬프트 선택"

승인 FAQ가 수백 건 규모라 질문 목록 전체를 프롬프트에 넣고 모델이 관련 번호를 고르는 방식을 택했습니다. 벡터 DB·임베딩 컬럼 없이 단순하고, 의미가 같은 다른 표현(약어·동의어)에도 강합니다.

검색 흐름 (createSearchFaq)

  1. 승인 FAQ 인덱스(id·질문·다른 표현·인증 종류, 답변 제외)를 5분 TTL 캐시 + 지문(개수+최신 수정 시각)으로 최신성 확인 → 다른 서버 인스턴스의 수정도 즉시 반영
  2. 어휘 일치 보정(lexical.ts): 질문이 FAQ 질문·다른 표현과 사실상 같으면(8자 이상, 60% 이상 일치) 모델과 무관하게 먼저 포함 (긴 목록 뒤쪽 항목 누락 방지, 최대 3개)
  3. 모델 선택(Haiku, temperature 0, max_tokens 100): 번호 JSON 배열만 출력. FAQ 목록 블록은 프롬프트 캐싱(cache_control: ephemeral) 대상
  4. 공통 FAQ 보충: 특정 인증 FAQ가 뽑혔고 모두 공통은 아니면, common 항목만 모은 목록으로 두 번째 선택을 병렬 실행해 절차·서류 같은 공통 정보를 채움
  5. 합치기: 어휘 일치 → 모델 선택 → 공통 보충 순, 중복 제거, 최대 6건. 선택된 id의 답변은 그때 한 번에 조회

견고성 장치

  • 잘린 응답 허용 파서: 모델이 번호를 너무 많이 내서 [2, 3, 10 …처럼 닫는 괄호 없이 끊겨도, 읽을 수 있는 앞쪽 번호만 쓰고 SELECT_MAX=5로 자름 (이 오류로 고객 응답이 실패하지 않음)
  • 목록에 없는 번호·중복은 버림
  • 선택 규칙(lib/prompts/select.ts): 같은 정보 종류(비용/절차 등)만, 인증 종류가 다르면 제외, [공통] 항목은 모든 인증에 해당, 복합 질문은 부분마다 하나 이상, 개요 질문은 분야를 골고루
  • 선택은 "고르는 것"일 뿐 답은 쓰지 않으므로, 프롬프트 주입이 있어도 고정 문구 경로를 바꾸지 못함
교체 지점 · 전환 기준 검색 로직은 searchFaq() 인터페이스 뒤에 격리되어 있어 벡터 검색으로 바꿔도 이 모듈 안에서만 수정하면 됩니다(CLAUDE.md 규칙: 임베딩 코드·컬럼을 임의로 추가하지 않음). 질문당 비용·지연이 FAQ 수에 비례하므로, 승인 FAQ가 약 500건을 넘거나 회귀 테스트가 반복 실패하거나 지연·비용이 예산을 넘으면 전환을 검토합니다. 현재 440~460건 규모에서 대표 질문 42건이 모두 통과했습니다.

접근 제어 (이중 방어)

DB — RLS

모든 테이블 RLS 활성. 익명(anon)에게는 승인된 FAQ의 지정 컬럼만 읽기 허용(컬럼 단위 GRANT). 나머지는 정책 없음 = 서버(service role)만 접근. 요청 제한 함수는 service_role만 실행 가능.

서버 — 계층 분리

DB 접근은 lib/db/만, 서버 클라이언트는 server-only import 가드. service role 키는 NEXT_PUBLIC_ 접두사 없이 서버에만. 관리자 API는 api-guard, 서버 액션은 requireAdmin()으로 이중 확인.

네트워크 — 헤더·제한

nosniff, Referrer-Policy, Permissions-Policy, HSTS. /chat만 iframe 허용(CHAT_FRAME_ANCESTORS로 제한 가능), /admin은 frame-ancestors 'none', 그 외 'self'. 로그인·채팅 IP별 제한.

관리자 로그인 Supabase Auth 매직링크(signInWithOtp). 허용 이메일(ADMIN_ALLOWED_EMAILS)에 없으면 메일을 보내지 않되 응답은 동일(관리자 주소 추측 방지). 미들웨어는 쿠키를 믿지 않고 getUser()로 토큰을 Supabase에 검증하고, 허용되지 않은 계정은 세션 쿠키를 제거합니다.

8문서 → FAQ 초안 파이프라인

운영자가 인증 안내서·절차서 같은 파일을 올리면 근거 문장이 확인된 FAQ 초안만 만들어 줍니다. 문서는 답변의 근거가 아니라 초안의 재료이고, 고객에게 나가는 것은 사람이 승인한 FAQ뿐입니다.

1
업로드 Storage + documents

최대 20개·파일당 20MB, 형식 검사. 브라우저가 SHA-256을 계산해 서버에 전달 → 서버도 재계산해 내용이 같은 파일은 차단(이름이 달라도). 이름만 같고 내용이 다르면 개정판(version, supersedes)/별도 문서/취소를 선택. 업로드 시 MIME을 확장자로 정규화(브라우저가 이상한 MIME을 보내는 경우 대비).

2
추출·조각화 lib/extract

형식별 추출기(PDF/DOCX/XLSX/PPTX/텍스트) → 문단 단위 chunk(쪽·섹션 제목 보존). 스캔 PDF는 쪽당 평균 50자 미만이면 추출 실패로 처리(원본 요청). 텍스트와 조각은 finish_doc_extraction RPC로 원자적 교체.

3
초안 생성 Sonnet 5.5

조각 5개씩(질문·답변 자료는 10쌍씩) 배치로 호출, 조각당 최대 3건. 작업 상태를 generation_jobs에 저장해 화면을 닫아도 이어서 진행(락·재개), 문서당 최대 50건. narrative(설명 자료)는 모델이 질문을 만들고, qa_pairs(Q&A 문서)는 질문·답변을 원문 그대로 가져옴.

4
선별(screening) — 자동 탈락 핵심 안전장치
근거 문장 대조원문에 글자 그대로 있어야 함
숫자 대조비용·기간 수치가 원문과 같아야 함(strictNumbers)
컨설팅성 제외"통과 방법" 류 초안 불가
타 기관 안내 제외IGSC 소관이 아닌 제도
중복 제외같은 인증의 기존 FAQ와 같은 질문(Haiku로 의미 비교)

근거가 없으면 답을 지어내지 않고 빈 답변의 '보완 필요'(needs_input) 초안으로 남깁니다. 탈락 항목은 사유·원문과 함께 보존되어 운영자가 직접 작성으로 이어갈 수 있습니다.

5
검수 → 승인 사람

문서 단위 검수 큐(카드에서 수정·승인·보류·삭제, 원문 보기에서 근거 문장 하이라이트, 키보드 A/S/D). 승인하면 즉시 챗봇에 반영되고 승인자·시각이 기록됩니다.

6
개정 대응 재검토 표시

문서를 개정(또는 삭제)하면 그 문서로 만든 승인된 FAQ에 "재검토 필요" 표시만 붙고 답변은 계속 서비스됩니다. 새 문서로 초안을 다시 만들어 기존 답변과 나란히 비교한 뒤 채우기/변경 없음으로 처리.

추가 사항: 중복 방지·일관성 규칙
  • FAQ 직접 등록·수정 시 같은 인증 종류의 의미가 같은 질문을 찾아 "비슷한 FAQ가 있습니다" 경고(저장은 막지 않음).
  • 같은 질문이라도 인증 종류가 다르면 중복이 아님. 같은 인증 코드 안에서도 질문에 드러난 대분류(식품 비건/화장품 비건)가 다르면 별개로 처리.
  • 이미 초안을 만든 문서를 다시 처리하면 이전 자동 초안만 교체하고, 수정해 둔 초안·미답변에서 만든 초안·승인된 FAQ는 보호(초안 메모 접두사로 구분).
  • 문서에서 만든 FAQ가 모두 승인되면 "FAQ 초안 만들기" 버튼이 승인 완료 표시로 바뀜(남은 작업이 있으면 다시 노출).

10운영 기능

요청 제한 lib/rate-limit.ts · 0011

  • DB 고정 구간 카운터(RPC rate_limit_hit, 원자적 upsert) — 서버리스 인스턴스 간 공유
  • 채팅: IP 분당 15 · 시간당 120 · 전체 하루 3,000(AI 비용 보호). 관리자 로그인: IP 10/시간, 이메일 5/시간. 모두 환경 변수로 조정
  • 키는 해시(IP·이메일 원문 저장 안 함). DB 오류 시 인스턴스 메모리 제한으로 폴백(제한이 꺼지지 않게)

모니터링·알림 lib/monitor

  • /api/health: DB·AI 점검(AI는 5분 캐시), 외부 가동 감시용(503이면 이상)
  • /api/cron/monitor(Bearer CRON_SECRET): 신호 수집 → 순수 함수 evaluate()로 판정(AI 실패·DB 실패·오류율·상한 도달 = 긴급, 승인 FAQ 0건·미답변 적체 = 주의) → Resend 메일/웹훅. 같은 문제는 6시간 쿨다운(요청 제한 RPC 재사용)
  • 실제 사고(AI 크레딧 소진 시 모든 질문이 조용히 담당자 이관)에서 출발한 설계

유입 채널 추적 lib/channels.ts · 0012

  • 링크 /chat?src=채널&c=캠페인 → 클라이언트가 탭 세션에 저장해 모든 요청에 첨부, 서버가 허용 목록으로 정규화(모르는 코드는 other, 형식 위반은 버림)
  • 링크에 src가 없으면 Referer로 블로그·링크드인·인스타그램 추정. 위젯은 data-src(기본 homepage)
  • 0012 적용 전에도 대화 기록이 깨지지 않도록 insertChatLog가 컬럼 부재 시 채널 없이 재시도

위젯 public/widget.js

  • 스크립트 한 줄 삽입. Shadow DOM으로 고객사 CSS와 격리, 패널은 /chat iframe(첫 클릭 시 로드), 480px 이하 전체 화면

프로젝트 규칙 (CLAUDE.md)

  • API 라우트는 app/api/, 비즈니스 로직은 lib/에 분리. DB 접근은 lib/db/를 통해서만.
  • 시스템 프롬프트는 lib/prompts/에 상수로 분리(코드에 인라인 금지). 고정 안내 문구도 messages.ts 한 곳에.
  • 에러는 삼키지 않고 로깅 후 사용자에게는 담당자 연결 안내.
  • 검색 방식은 프롬프트 선택(임베딩 금지) — 교체 범위는 searchFaq() 모듈로 한정.

  • 순수 함수 + 얇은 I/O 껍데기: evaluate(), aggregateChannels(), screenItem(), parseSelection(), normalizeSource() — 로직은 순수, DB·네트워크는 주입.
  • 의존성 주입: runChat/createSearchFaq/문서 파이프라인이 deps를 받아 테스트에서 stub.
  • 점진적 호환: 새 컬럼 의존 코드는 컬럼이 없을 때도 핵심 동작이 유지되도록 폴백(채널 기록, 지표 수집 등).
  • 고정 문구 우선: 모델 출력에 의존하지 않는 응답은 상수로. 모델 출력은 센티널·정규화·검증을 거쳐서만 사용.
